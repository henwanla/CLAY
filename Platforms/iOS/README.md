# CLAY iOS 配置检查

这个预览应用把 CLAY 的节点解析器带到 iPhone 和 iPad。粘贴节点分享链接、Base64 链接列表、内联节点形式的 Clash/Mihomo YAML 或 JSON，或 V2Ray/Xray JSON 出站，即可看到可解析的节点数量、协议分布和问题类别。也可以用内置示例验证：结果应显示一个兼容的 VLESS 节点和一项不支持的协议。

检查在设备上进行，文本最多 2 MiB，结果只显示汇总。粘贴的内容不会写入应用文件；点「清除输入」会清空输入和结果。离线目标不下载订阅，不执行分流规则或提供器，不启动代理或 VPN，也不判断节点能否连通。界面随系统语言提供简体中文、英文和日文。

在 macOS 安装完整 Xcode 和 iOS Simulator SDK 后，可从仓库根目录构建：

```sh
xcodebuild -project Platforms/iOS/CLAY.xcodeproj -scheme CLAY \
  -configuration Debug -destination 'generic/platform=iOS Simulator' \
  CODE_SIGNING_ALLOWED=NO build
```

最低系统版本为 iOS/iPadOS 16。仓库附带 iOS Simulator 构建工作流；其构建产物用于开发验证，没有签名、真机安装或商店分发流程。

## IPv4 包转发实验 / Experimental IPv4 packet bridge

`Engine/` 提供 Packet Tunnel 实验使用的转发库。离线目标 `app.clay.offline` 不链接它。通用桥只接收 CLAYCore 生成的节点和规则，拒绝原始配置、不认识的字段和 IPv6 包。它不开放代理／控制监听，不保存节点资料，也不输出内核日志。通用桥在启动时应用节点与规则；隧道实验使用独立的单节点转发路径，可更新当前会话。

The bridge is separate from the offline app. It accepts only the normalized node list and rules generated by CLAYCore. It opens no local proxy or controller, writes no profile, and suppresses engine logging. The general bridge accepts raw IPv4 packets and applies a node and rules at start. The Tunnel Lab uses a separate single-node path that can update a running session.

在 macOS 上用 Go 1.24.3 和 [固定的 Mihomo v1.19.34 源归档](https://codeload.github.com/MetaCubeX/mihomo/tar.gz/refs/tags/v1.19.34) 复验（脚本检查 SHA-256）：

```sh
engine=Platforms/iOS/Engine
archive=/path/to/mihomo-v1.19.34.tgz
out="$(mktemp -d)"
bash "$engine/build.sh" "$archive" host-test "$out"
bash "$engine/build.sh" "$archive" host-race "$out"
bash "$engine/build.sh" "$archive" macos "$out"
bash "$engine/link-check.sh" macos "$out"
bash scripts/swift-local.sh build -c release --product CLAYCoreChecks
.build/release/CLAYCoreChecks --packet-fixture | "$out/abi-smoke"
```

宿主 Go 回归用 Swift 导入同一份合成 Clash 节点列表，再通过包转发桥连接回环上游。VMess、VLESS、Shadowsocks AEAD、Trojan TLS 与普通／Salamander／Gecko Hysteria2 均实际传输 IPv4 TCP；除 Shadowsocks 夹具外也验证 UDP。通用桥在规则和全局模式下按所选节点返回不同应答，无效证书、指纹或密码不会得到数据。Lab 另在同一会话内切过上述七种协议及变体的 TCP 节点，验证新连接走新节点、旧上游连接关闭，以及错误会话和无效配置不替换当前节点。C 链接测试验证 Swift 配置和桥接接口，GitHub 用两个 iOS SDK 分别验收 ARM64 链接。宿主流量测试不代表真机、直连流量、域名规则、系统 DNS 或 VPN 退出恢复已验收。

The host test imports a synthetic Clash profile with the shared Swift code, then sends IPv4 through the packet bridge to local protocol servers. It checks TCP for VMess, VLESS, Shadowsocks AEAD, Trojan TLS and Hysteria2 (plain, Salamander and Gecko), plus UDP for all except the Shadowsocks fixture. It verifies routing to the chosen node on each start and rejects untrusted certificates, mismatched pins and wrong passwords. The Lab tests switch between all seven TCP variants within a single packet session, check that the previous upstream socket closes, and verify that invalid updates leave the previous node in place. Neither the host tests nor the iOS SDK link checks exercise the device VPN or system DNS.

TUIC v5 的两种 UDP 中继（native、quic）也已在同一组宿主测试中通过 TCP 与 UDP 验证，并纳入 Lab 在线切换的 TCP 回归。错误密码、错误证书指纹及无指纹的自签名证书均不能取得应答。Lab 每次连接只开放一个指定的 IPv4 或 IPv6 端点。IPv6 已用两个回环 VLESS 节点验证 TCP、UDP、节点切换和旧套接字关闭。

Both TUIC v5 UDP relay modes (native and quic) now pass TCP and UDP in the same host suite and TCP live switching in the Lab. Wrong passwords, mismatched certificate pins, and unpinned self-signed certificates yield no response. The Lab exposes one explicitly selected IPv4 or IPv6 endpoint per connection. Host tests verify IPv6 TCP and UDP through two loopback VLESS nodes, live switching, and closure of the old sockets.

Shadowsocks 2022 的三种密码套件，以及 AES-128／AES-256 的服务器与用户双密钥，都在宿主包转发桥上通过了 IPv4 TCP 和 UDP。实验已验证在线切换至这些节点后的 TCP 和 UDP 转发；错误用户密钥无法取得应答。真机尚未复验。

The host packet bridge verifies IPv4 TCP and UDP for three Shadowsocks 2022 suites and both AES suites with server and user keys. The Lab can switch into all five variants while connected and forward TCP and UDP. A wrong user key yields no response. These checks do not run on an iPhone.

宿主回环也验证了带认证的 HTTP CONNECT、SOCKS5 和两者的 TLS 形式。在线换节点后仍可用同一个隧道建立新的 TCP 连接；错误密码、不受信任的证书或错误的证书指纹均无法取得应答。此四种上游不转发 UDP。

The host loopback suite also switches between authenticated HTTP CONNECT and SOCKS5 upstreams, including their TLS variants. TCP works through the new node while the tunnel stays up. Wrong credentials, untrusted certificates, and incorrect pins fail. These upstreams do not forward UDP.

CI repeats Lab TCP and UDP switching and restart tests with Go's race detector, then checks arm64 linkage for both iOS SDKs. The build applies [a small patch to the pinned Mihomo source](Engine/tuic-v5-packet-close.patch) so closing a TUIC v5 UDP association can safely interrupt a concurrent read. Before distributing a binary, include the corresponding Mihomo source, this patch, bridge source, build instructions, and required license files.

## CLAY 隧道实验 / CLAY Tunnel Lab

另一个 Xcode scheme `CLAYTunnelLab` 打包自己的 Packet Tunnel 扩展，与离线 App 分开。界面支持中文、英文和日文。用户在启动前输入一个 IPv4 或 IPv6 字面地址及端口、选节点和模式；也可使用演示端点 `198.51.100.42:18080` 或 `[2001:db8::42]:18080`。连接后界面从扩展读取实际端点。更换端点要先停止再连接。在线应用节点或模式保留当前端点，关闭旧上游连接，后续 TCP 连接和 UDP 数据报使用新节点。已排队的旧包仍可能到达应用。只有扩展确认后才显示已应用；未确认时可重试或停止。

系统为所选地址加入一条主机路由（IPv4 `/32` 或 IPv6 `/128`）。**该地址的所有流量**都会进入扩展，只转发所选端口的未分片 TCP，以及节点支持的 UDP；IPv6 扩展头不在实验范围内。该地址的其他端口和协议在连接期间不可用。规则和全局模式均只通过所选节点转发这个端点，没有直连回退。不支持 UDP 的节点会丢弃 UDP。不会修改 DNS 设置，也不加入默认路由或另一地址族的路由。系统 VPN 配置只保存扩展标识和固定标签；地址和端口只随手动启动发送，不写入缓存或日志。节点凭据只随手动启动或应用更新发送给扩展。启动可能暂停其他 VPN。

使用自定义端点时，用自己的客户端验证。内置探测只对两个演示端点发送明文夹具标记。代理节点的服务器地址应与目标地址不同；实验会拒绝相同的字面地址，不会主动查询域名来判断它是否解析到目标地址。它用于在受控环境验收代理接入。

The separate `CLAYTunnelLab` scheme embeds a Packet Tunnel extension. Enter one numeric IPv4 or IPv6 address and a port before starting, or use either demo endpoint: `198.51.100.42:18080` or `[2001:db8::42]:18080`. The app reads the active endpoint back from the extension. Stop and reconnect to change it. Applying a node or mode while connected preserves the endpoint and closes old upstream connections. Wait for the acknowledgment before testing with a fresh connection. New TCP connections and later UDP datagrams use the new node; packets already queued may still reach the app.

The OS claims **all traffic to the selected address** using one host route (IPv4 `/32` or IPv6 `/128`). The Lab forwards only unfragmented TCP and supported UDP for the selected port, and excludes IPv6 extension headers. The address's other ports and protocols are unavailable until the tunnel stops. Rule and Global both send this endpoint through the selected node without direct fallback. UDP traffic is dropped if the node does not support it. The Lab leaves DNS settings, default routes, and routes in the other address family alone. VPN preferences contain only the fixed label and provider identity. The endpoint stays out of caches and logs; node credentials go to the extension only on an explicit start or apply. Starting may pause another VPN.

Use your own client for a custom endpoint. The built-in plaintext test marker goes only to the two demo endpoints. Use a proxy server at a different address from the selected destination: the Lab can reject a matching literal address, but does not look up proxy hostnames to detect a match. Use the Lab in a controlled test environment.

### 订阅 / Subscriptions

在隧道实验打开「订阅」，输入 HTTPS 地址，点「下载并保存」。从保存的订阅点「使用缓存」，再选节点并启动，或在已连接时应用到测试隧道。刷新只更新本机缓存，要重新选用才会影响草稿；正在运行的线路还须手动应用。下载失败保留上一份缓存。无可用网络时也可以选已有缓存，或者直接粘贴节点。

订阅仅手动下载，信任系统 TLS 验证，只跟随同源跳转，解析前限制内容为 2 MiB。地址、名称和节点文本在 App 的私有目录以 AES-256-GCM 保存，目录排除系统备份；密钥保存在仅本机且解锁时可访问的 Keychain。缓存不交给扩展，扩展只接收一次操作选中的节点。若缓存无法解密，可以在列表删除它再添加。离线检查目标没有订阅入口。

In Tunnel Lab, save an HTTPS subscription, use the saved copy, and then choose a node. Refresh saves a new copy without changing the draft or a running tunnel. Re-select the cache and apply explicitly to switch. Downloads are manual, use system TLS verification and same-origin redirects, and cap the decoded response at 2 MiB. Cache records are encrypted in the app, excluded from backups, and use a device-only Keychain key that requires the device to be unlocked. The offline checker has no subscription controls.

在 macOS 运行 `bash Platforms/iOS/TunnelLab/check-subscriptions.sh`，用合成响应验证加密、跨记录替换拒绝、无效刷新保留原件和并发删除。签名真机还应验证保存后重启 App 能离线选用、锁屏时无法读写、重新解锁后可恢复，以及正常刷新和连线状态彼此独立。

有完整 Xcode 时，从仓库根目录构建未签名的设备目标。模拟器将两个 SDK 参数分别换成 `iphonesimulator` 和 `generic/platform=iOS Simulator`：

```sh
engine=Platforms/iOS/Engine
archive=/path/to/mihomo-v1.19.34.tgz
out="$(mktemp -d)"
bash "$engine/build.sh" "$archive" iphoneos "$out"
xcodebuild -project Platforms/iOS/CLAY.xcodeproj -scheme CLAYTunnelLab \
  -configuration Debug -destination 'generic/platform=iOS' ARCHS=arm64 \
  CODE_SIGNING_ALLOWED=NO CLAY_PACKET_ENGINE_DIR="$out" build
```

真机验证 / Device validation:

1. 给 App 和扩展使用同一个开发团队，在两个标识上启用 Packet Tunnel entitlement。必要时用 `CLAY_LAB_ID` 改为该团队可签名的包名，扩展会自动带上 `.provider`。使用签名构建安装到自有测试设备；CI 的未签名产物不能安装。
2. 在可信局域网运行 `python3 Platforms/iOS/TunnelLab/synthetic-upstream.py --bind <本机私有 IPv4>`。它生成临时 VLESS 测试链接，仅响应固定测试请求，不转发流量。粘贴它到 Lab，导入、选择、启动并按设备提示授权。不要使用真实订阅来跑这项验收。
3. 先使用 IPv4 演示端点，完成后停止并用 IPv6 演示端点重复。系统显示已连接、当前端点读回成功后点「发送 TCP 测试包」，需收到测试应答。运行第二份夹具，把两条临时链接各放一行。连接第一条后选第二条和另一个模式，点「应用到测试隧道」，确认 VPN 显示仍连接。关掉第一份夹具并重新发送测试包，仍应收到应答。另复验停止、重启、拒绝和撤销权限。退出时关闭夹具。
4. 停止后，用自己控制的 IPv4 和 IPv6 TCP／UDP 服务分别重复测试。测试 UDP 时，选支持 UDP 的节点，并在换节点前后复用同一个客户端套接字。确认重开 App 能读回实际端点、同地址的其他端口不转发、另一地址仍用原路由、停止后原路由恢复。设备上的路由、DNS、IPv6、后台生命周期和内存尚待确认。

Use signing profiles that entitle the app and extension on the same team. On a trusted LAN, run the fixture with the Mac's private IPv4 address and import its temporary link in the Lab. Start with the IPv4 demo, authorize the VPN on the device, wait for the active endpoint to appear, and tap “Send TCP test packet.” Stop and repeat with the IPv6 demo. Repeat with two fixtures: apply the second node and another mode, check the system VPN remains connected, stop the first fixture, and send a fresh probe. Stop the VPN and remaining fixture when finished. Repeat with separate controlled IPv4 and IPv6 TCP and UDP services. For UDP, select a capable node and reuse the client socket while switching nodes. Also verify: verify readback after reopening the app, refusal on other ports at the same address, a separate address staying on its normal route, and route restoration after stopping. Unsigned CI builds check packaging only; they do not prove that an iPhone can run the tunnel.
