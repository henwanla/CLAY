# CLAY 公开仓库安全维护

调研日期：2026-11-25。这份清单是维护建议，不表示远端保护、告警、签名或发布证明已经启用。公开只记录做法和结果；未修复的具体问题通过私有渠道报告。

macOS 的 CI 在构建前检查 Git 索引，拦截常见访问令牌和私钥格式，也拦截认证文件、调试签名文件和本机安装包。可在提交前运行 `python3 scripts/check-source-privacy.py` 检查已暂存内容。日志只显示匹配数量；这属于防止误提交的一层检查，不能检测任意自定义密钥或未跟踪文件，也无法撤销历史中的泄露。

## 分支、贡献和权限

| 位置 | 建议配置 | 验证方法 |
| --- | --- | --- |
| Settings → Rules → Rulesets，目标 `main` | 建立 Active 分支规则：只能通过 PR 合入、禁止强推和删除、要求解决评审讨论、选中一次成功 PR 的 macOS 构建检查（本仓库工作流 `macOS checks`，job ID `build-and-check`；以 GitHub 实际状态名为准），来源锁到 GitHub Actions，要求分支在合入前基于最新基线。 | 建一笔只改文档的 PR，检查未通过时不能合入；通过时维护者可按规则合入。先不设签名提交强制规则，以免挡住当前迁移；有明确密钥和贡献政策后再单独启用。 |
| 同上，目标 `develop` | 单独建立 Active 分支规则：要求 PR、同一状态检查、禁止强推和删除。先确认团队准备好通过功能分支提交 PR，再启用以免打断既有直接推送的流程。 | 从功能分支对 `develop` 提 PR，确认检查触发。Windows/Linux 检查真正稳定后，再升级为必需项，避免绑定尚未稳定或可能被跳过的任务。 |
| 审核与例外 | 单人维护时，PR 和通过检查仍必须，先不要求另一人批准。维护团队有独立评审者后，为 `.github/workflows/`、`Vendor/`、`scripts/package-macos.sh`、`Package.swift` 设置 CODEOWNERS 并启用对应评审。默认不授予普遍绕过权限；如需紧急例外，明确维护者范围和使用记录。 | 核对由 PR 作者提交的新改动如何失去已有的批准；启用独立维护者审核后，验证作者不能独自绕过。 |
| Settings → Actions → General | 默认 token 只读，关闭让 Actions 创建和批准 PR 的设置。对公开贡献选择审核所有外部贡献者的工作流运行；执行 fork 代码仅用无发布权限的 GitHub 托管 runner，不给 fork PR 发凭据、写 token 或秘密。允许使用的 Actions 按需限制；支持时强制全 SHA，工作流保持最小权限。 | 检查 fork PR 跑的是常规 `pull_request`，工作流无 secrets，checkout 不保留凭据。发布凭据不应进入 PR 检查。 |

GitHub 官方：[Rulesets 可用规则](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets)、[CODEOWNERS](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners)、[管理 Actions 设置](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository)、[Actions 安全使用](https://docs.github.com/en/actions/reference/security/secure-use)。

## 发布完整性

1. 对 `v*` 标签设单独的 tag ruleset，阻止一般更新和删除。该规则和分支规则并行；启用后只从已通过检查的 `main` 提交新建版本标签，不移动已发布的标签。确认预发布也适用对应的维护流程；如需修复，发布新版本。
2. 从干净且精确到标签的检出构建；记录提交 SHA、标签、构建环境、发布 ZIP 的 SHA-256 以及独立内核依赖的版本。解包检查可执行架构、许可、签名和文件清单。CI 构建和上传的是不同 ZIP 时不要混称为同一产物；保留上传 ZIP 的来源证据。
3. 适用时在 Settings 启用 [Immutable releases](https://docs.github.com/en/code-security/how-tos/secure-your-supply-chain/establish-provenance-and-integrity/prevent-release-changes)；只对之后发布的版本生效。先建草稿、上传所有文件并核对摘要，再发布。它保护发布标签和资产；下载旁边的 SHA 文件可查损坏，不能独立证明发布者身份。
4. 条件成熟后单独做受保护标签的构建／发布工作流，保存并发布同一个校验过的产物，考虑生成 [GitHub 构建产物证明](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations) 并给出验证命令。公开 PR 工作流继续只读。Developer ID 签名和公证是 macOS 发行的另一层校验，不能用临时签名或 GitHub 的资产校验代替。

## 依赖及漏洞响应

- 内核、Actions 与 vendored 代码的改动放在易审阅的 PR；说明来源、版本、摘要、许可及回退版本。从可信上游提取固定版本并比较字节；只更新锁定记录不算验收。这些文件的审查不能仅靠自动依赖告警。公开 ZIP 默认不附内核；移动端集成与内核再分发另做许可检查。
- 在可用时打开 [Private vulnerability reporting](https://docs.github.com/en/code-security/security-advisories/working-with-repository-security-advisories/configuring-private-vulnerability-reporting-for-a-repository) 和 [Push protection](https://docs.github.com/en/code-security/secret-scanning/protecting-pushes-with-secret-scanning)；维护者不在公开 issue 请求节点、原始日志或令牌。定期核对官方上游通告、版本兼容与复现测试。若发现实际凭据暴露，先停止使用、吊销和轮换，再记录后续处置。
- 依赖或权限变更后跑现有测试、复核实际发布包，更新验收记录；记录运行的环境和未验证项。公开公告应给出受影响版本、缓解措施和可安装的修复版本。
