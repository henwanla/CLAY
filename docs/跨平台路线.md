# CLAY 跨平台路线

更新日期：2026-11-27。公开安装包仍面向 macOS Apple Silicon。[iOS](../Platforms/iOS/README.md)保留离线检查，并有独立的 Packet Tunnel 测试目标，只接管保留的 IPv4 验收地址。[Android](../Platforms/Android/README.md)有离线、手动 Relay 与 IPv4 VPN 技术预览，已在 Android 15 模拟器验证授权、转发和停止等路径。[Linux GTK](../Platforms/Linux/README.md)有可选托盘及 GNOME、Plasma 6 的 PAC 接入与恢复；CI 分别验证 dconf、KConfig 和 libproxy，使用虚拟显示与隔离用户配置。[Windows 桌面](../Platforms/Windows/README.md)支持托盘、手动代理和当前用户默认连接的 PAC 接入与恢复。移动真机、实际 GNOME／Plasma 桌面和浏览器验收仍待完成。

## 先把三个选择拆开

| 用户要选什么 | 一句话说明 | 路线 |
| --- | --- | --- |
| 应用怎样把流量交给 CLAY | 手动填 HTTP/SOCKS 地址、应用自设 PAC、启用系统 PAC，或以后用 TUN | 继续保留已有三种方式。TUN 是新权限和新阶段，不默默开。 |
| 内核如何路由收到的流量 | Rule 按规则、Global 走选定策略、Direct 直连 | 作为 Mihomo 运行策略；单独显示当前状态和命中结果。PAC 自行返回 DIRECT 的流量不会进入内核，切 Global 也不会覆盖那部分流量。 |
| 哪个节点实际出站 | 固定单节点、手动选组、以后自动测速或故障切换 | 先稳定选择和实际连通测试；节点身份与显示名分离。自动切换单独验收恢复、抖动和失败回退。 |

[Mihomo 模式定义](https://wiki.metacubex.one/en/config/general/)与[策略组](https://wiki.metacubex.one/en/config/proxy-groups/)提供这些设置的内核语义。[Clash Verge Rev](https://github.com/clash-verge-rev/clash-verge-rev) 可作为跨桌面端和托盘操作参考，[托盘源码](https://github.com/clash-verge-rev/clash-verge-rev/tree/c83f7ad529c7c9cb3d2d54a0955ef8c1b22a411b/src-tauri/src/core/tray)与现有[架构调研](架构调研.md)记录相关实现，比对时关注从托盘切策略是否同步到主窗口、退出是否恢复系统设置。[MetaCubeXD](https://github.com/MetaCubeX/metacubexd) 可参考如何组织流量、策略组、连接、规则和日志；CLAY 保留原生 UI 和自己的信息架构。两个上游均作为产品参考，不直接复用其界面代码或素材。

## 核心复用与权限边界

1. **共同协议是数据和行为约定。** 固定有版本的节点、订阅快照、规则、事件与诊断格式。以同一批合成夹具验证导入、停机、路由、脱敏、连接字段，先用现有 Swift 核心和最小便携 CLI 验证约定；UI 和不同语言的实现可以按需跟进，无需先重写 macOS App。已实现的协议与候选协议分别记录。
2. **桌面优先运行单独的官方 Mihomo。** 本地进程管理配置、鉴权状态和健康上报；入口和控制面默认绑定回环；上游二进制的选择、签名或摘要、回退版本要可核查。Linux 和 Windows 的便携 CLI 可启动已校验的前台内核、查看状态和切换节点及模式。macOS 桌面 App 管理自己的会话。GitHub 发布默认仍不附带内核。
3. **接入上游与导入配置是两件事。** [Mihomo 出站文档](https://wiki.metacubex.one/en/config/proxies/) 包括 VMess/VLESS、Shadowsocks、Trojan、Hysteria2、TUIC、WireGuard 等；现有 CLAY 只验证其中一部分。先逐种规范化，明确支持字段与拒绝原因。分享链接导入、Clash 内联节点、策略组、远程 provider、DNS 与完整配置执行分层验收。允许完整配置之前，先做明确授权、影响预览和独立的可信配置入口。
4. **可下载的二进制和应用集成是两件事。** 已核对 [v1.19.34 发布资产](https://github.com/MetaCubeX/mihomo/releases/expanded_assets/v1.19.34)、[固定构建配方](https://github.com/MetaCubeX/mihomo/blob/v1.19.34/Makefile)、[GPL v3 许可](https://github.com/MetaCubeX/mihomo/blob/v1.19.34/LICENSE)。发布资产有 macOS、Linux、Windows 和 Android 目标；这些对各自宿主运行有参考价值，但不证明该内核已适合手机应用扩展。若要再分发内核、修改内核或将其静态／动态链接进 App，应先确定对应源代码、构建输入及许可义务，尤其是商店发行与闭源模块的边界；此项需独立审核。
5. **网络入口和系统集成由各端实现。** 保存原设置、可恢复地启用、明确显示当前路由范围、停止时归还所管理的设置。不要把系统 PAC 和 TUN 当成同一个开关，也不要从另一个平台的成功推断此平台的权限和生命周期。

| 3：Windows / Linux 桌面 | 保留同一节点、规则和遥测格式，先手动代理→托盘→平台系统代理。两个系统的安装、权限、崩溃恢复各验一次 | Windows 用 [WinINet 的连接设置和 PAC](https://learn.microsoft.com/en-us/windows/win32/api/wininet/ns-wininet-internet_per_conn_optiona) 验证遵循系统设置的应用；不把 WinHTTP 服务当成同一配置。首轮 x64、后续独验 arm64；评估 [Windows 代码签名与 MSIX](https://learn.microsoft.com/en-us/windows/msix/package/sign-app-package-using-signtool)。Linux 先选择 Ubuntu x86_64 作可复验基线，前台模式保底；托盘按 [StatusNotifierItem](https://specifications.freedesktop.org/status-notifier-item/latest/) 的可用宿主单测；GNOME/KDE、Wayland/X11 不能互相代替。Linux TUN 创建和路由另设权限检查，遵循[内核 TUN/TAP 文档](https://docs.kernel.org/networking/tuntap.html)，不让整个 GUI 以 root 运行。 |

| 5：iOS / iPadOS 原型 | SwiftUI 壳加 Network Extension Packet Tunnel Provider；把系统包流和内核连接交给扩展，桌面子进程方案不作为移动实现基线 | 对照 Apple [TN3134](https://developer.apple.com/documentation/technotes/tn3134-network-extension-provider-deployment)和 [Packet Tunnel Provider](https://developer.apple.com/documentation/networkextension/nepackettunnelprovider)。先过正确 entitlement、签名、真机连接与撤销、休眠恢复、内存和路由验证。[App Review 5.4](https://developer.apple.com/app-store/review/guidelines/#vpn-apps)要求 VPN 服务由组织开发者提供，并事先说明数据处理；发行资格单独确认。未验证签名、真机和商店资格。 |

顺序理由：当前已有 macOS 用户路径和回环夹具；先让 CLI 与原生 App 共享行为约定，再加一套 Windows/Linux 平台外壳，比较重复实现成本。Android 和 iOS 都需要真实 VPN 生命周期、签名、权限与发行验证，不能用命令行包或跨平台 UI 演示代替。若开始 macOS TUN，也先按 [TN3134 发行矩阵](https://developer.apple.com/documentation/technotes/tn3134-network-extension-provider-deployment) 决定适用的打包与签名方案。

## Linux 前台试用

`clay-portable mihomo-run FILE NODE_NUMBER MIHOMO SHA256` 选择导入后第 `NODE_NUMBER` 个兼容节点（从 1 开始）。`MIHOMO` 是你明确选择的本机可执行文件；`SHA256` 从可信上游发布记录核对。需要可执行的 `/tmp`、`/usr/bin/sha256sum` 和可读取的子进程 `/proc`。命令工作在普通用户权限下，也支持 `--proxy-port` 和 `--control-port`。

就绪后把显示的代理回环地址填进需要代理的应用。默认只加载选中的节点；加上 `--all-nodes --interactive` 可在运行中输入 `node N` 换节点，输入 `mode rule|global|direct` 切换流量模式，输入 `status` 查当前状态，输入 `quit` 退出。交互需要 `/usr/bin/curl`，修改会通过本机控制接口读回确认。可用 `--mode` 指定启动模式，用 `--pac-rules FILE` 把本地规则文本用于内核的规则模式；它不会启动 PAC 服务，也不会修改系统代理。

控制接口使用随机密钥，不会在终端输出。会话退出、收到 Ctrl-C 或 SIGTERM 时，CLAY 清理该次会话的配置；若被 SIGKILL 或断电，不能依赖此清理，也可能留下子进程。GTK 托盘复用这个会话；只有收到应用图标注册确认且宿主存在时才隐藏窗口。托盘失去宿主会恢复窗口。GNOME 或 Plasma 6 的系统 PAC 由 GTK 桌面端明确启用，CLI 本身仍只提供手动接入。

## 付费优先级（假设，待验证）

- 免费保留基本连接、订阅、PAC、流量仪表、恢复和安全更新。首个付费候选是**本地网络诊断包**：节点变化时间线、失败原因对比、可单独选字段的脱敏报告、PAC/模式解释。先给自带节点的用户试用；看能否自行解决过去需要反复切节点的问题，记录使用频次和是否愿为省下的排查时间付费。
- 第二个候选是**可回滚的工作区配置**：保存多套订阅、规则和代理策略，浏览差异后切换，支持本地导出与恢复。先确认多人／多设备迁移的真实需求，再考虑加密同步。默认不收集用户连接、域名、凭据或订阅 URL。
- 两个候选均没有收款渠道或收入证据。先做小规模试用和访谈；不存在有效需求时停掉该候选。付费不靠操控用户流量、按访问内容投广告或出售遥测；移动发行和支付路径确定后再审具体商店政策。
